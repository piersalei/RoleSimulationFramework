# 心理学与工程的交付接口

心理学同学最有价值的交付是**字段含义、触发条件、行为锚点与反例**。工程侧再将其转为数据结构、调度和验证；暂不要求心理学同学直接写代码。

## 人物制作

复制 `roles/role1.json`，改名为新编号（如 `roles/role3.json`，文件名必须等于 `persona.id`），在其中的 `persona`（persona schema 2.0）里修改人物身份、公开描述、自我理解、相关分面、动机基线、价值权重和核心目标。`stable.module_status` 必须列出全部登记模块：有值的写 `active` 并在 `provenance` 里给来源；没有资料的写 `unknown` 且值为 `null`，不要写成 0 或中性值；本版没有建模的写 `not_modeled` 并说明原因。运行 `validate` 后再 `compile` 检查视图。模板内的数值是虚构示例，应逐项审定，不是默认人群常模。示例由 `PYTHONPATH=. python3.11 scripts/bootstrap_examples.py` 重建。

字段规则：

- `values.schwartz_priorities.weights`：只列已设定的施瓦兹价值，权重非负且和为 1；未列出的价值是 unknown，不是 0。
- `core_goals`：1–3 个，每个有 `priority`、`stability`、`source`，至多 2 个支持子目标（带 id 与上位链接）。
- `speech_style`：`baseline.directness` 加 `situational_rules`（`when` / `style` 列表），后者会进入表达阶段的风格约束。
- 71 维、发展位置、荣格功能、道德推理、文化取向：没有适配器，只能是 unknown / not_modeled / disabled。
- 旧的 1.0 档案会被拒绝；请按 2.0 重建，不做静默转换。

| 交付内容 | 必须说明 | 好的示例 |
|---|---|---|
| 主字段 | 构念、尺度、来源、是否测量 | “焦虑分面 1.2，角色设计值，非量表结果” |
| 自我理解 | 角色会如何解释自己 | “我只是需要弄清楚再答应” |
| 通常倾向 | 概率性而非永久绝对规则 | “高不确定任务中更可能索取证据” |
| 触发条件 | 可见线索与关系条件 | “重要合作方连续两次未兑现承诺” |
| 压力变化 | 能力/策略如何受负荷影响 | “先减少承诺范围，仍不凭空推断恶意” |
| 例外 | 何时应改变默认反应 | “出现可核对的兑现记录后恢复小范围合作” |
| 可观察信号 | 台词、动作、延迟、选择 | “请求回执、提出分阶段交付、拒绝不可控承诺” |
| 不应出现 | 可证伪的错误表现 | “未收到记录便宣告对方已兑现” |

未知数值保留缺失理由。P1 的 30 分面仍要求全部赋值；示例未重点设定项为显式合成中性 `0`，与 71 维的“定义缺失、未赋值”不同。模块级的缺失已能用 `unknown`（null）表达，但分面级还不能；未来材料抽取模式需扩展分面级的 nullable 与缺失策略，不能将缺失测量静默写成中性。

### 角色文件：一个角色一个文件

角色放在 `roles/`，用编号命名（`role1`、`role2`……），具体是谁打开文件看。文件名必须等于 `persona.id`。

```json
{"format": "role-1.0",
 "persona": { "...": "persona schema 2.0，原样嵌入，与心理学组约定的格式一致" },
 "skills": [{"name": "verify-before-commit", "priority": 0.95, "note": "核查偏好高、审慎分面高"}],
 "setup": {"goal": "…", "disclose": [], "conceal": [], "recap": []}}
```

- `persona`：上面的人物档案，校验规则不变。
- `skills`：这个人物会用哪些 skill、优先级（0–1）、为什么（`note`）；可以为空列表。skill 本身在 `library/skills/<name>/SKILL.md`，格式见 [08-persona-skills-survey.md](08-persona-skills-survey.md) 第 4 节。skill 是工程侧拟定的，`note` 里写明未经心理学组审定。
- `setup`：角色进入剧情时的开场设定，见下节；可以为 `null`。

用 `python3.11 -m rolesim validate role1` 校验整个角色文件，`python3.11 -m rolesim skills role1` 只看 skill。新写一个 skill：在 `library/skills/` 下建同名目录和 `SKILL.md`，`rolesim-source` 必须引用 `data/catalog.json` 里存在的章节，正文必须有"决策要点 / 表达要点 / 不会做的事 / 边界"四节（纯表达类可省略决策要点）。

### 开场设定（setup）

开场设定是角色自己知道和想要的东西，所以跟着角色走，不写在剧情里。

| 字段 | 含义 | 去向 |
|---|---|---|
| `goal` | 角色在这场互动里的目标 | 决策提示；表达提示 |
| `disclose` | 想让对方知道的信息（`id`、`text`、`markers`） | 决策提示（`want_known`）；表达提示（`may_share`） |
| `conceal` | 角色知道、但不想让对方知道的信息；`strategy` 只能是 `omission`（遗漏）或 `strategic_ambiguity`（战略模糊），不支持直接说谎 | **只进决策提示**（`keep_private`），表达提示拿不到原文 |
| `recap` | 前情提要，id 以 `recap:` 开头 | 作为记忆的第一批条目，可被决策引用为证据 |

`markers` 是自动审计用来检测"说出来了"的关键词（至少两个字）。前情提要里不能出现隐瞒条目的关键词，因为前情会进入表达提示。审计项 `concealed_info_withheld` 检查隐瞒内容没有进入表达提示、没有被说出；`disclose` 条目被说出只统计不判错。关键词检测抓不到换了说法的泄露，这部分仍需人工评分。

开场设定是写给角色本人看的："你""你方"都指角色自己这一方。内容要和角色坐的座位对得上：role1 的设定是项目组一方的，role2 是合作方一方的。程序只能检查 id 是否与环境事件冲突，内容是否相符要作者自己保证。

## 场景文件：背景，不指导角色

场景放在 `scenes/`，同样用编号命名（`test1`、`test2`……），文件名必须等于场景 `id`。场景只给背景和座位，**没有剧本，也不给角色下指令**；之后说什么、怎么发展由两个角色自己决定。正式格式以后按场景组的背景文件接口替换；目前用 scene schema 2.0 作为替身：

| 字段 | 含义 |
|---|---|
| `background` | 在场各方都知道的背景，作为合同里的 `scene_context` 传给每个角色；写事实，不写"你要……" |
| `seats` | 两个座位，各有 `id` 和 `title`（如"项目组数据负责人""合作方负责人"）；角色按座位顺序入座，双方互相只知道对方的座位名 |
| `max_turns` | 最多发言几次（两人轮流，2–40）；任何一方选 `close` 也会结束 |
| `allowed_actions` | 可选的交流动作：索要证据、提问澄清、提出方案、说明边界、暂缓、接受、结束 |
| `world_private` | 世界私有数据，永不进入任何角色的模型调用 |

旧的 1.x 场景（带 `events`、`partner` 等脚本字段）会被拒绝。

环境只做三件事：开场时发一条旁白；把一方说的话原样转给另一方；到轮数上限或有人结束时收尾。它不替任何一方说话，也不编造"对方同意了""记录已到"这类结果。一方说的话是另一方收到的唯一新事件。

## 换角色、换剧情

```bash
python3.11 -m rolesim list                                          # 列出全部角色和剧情
python3.11 -m rolesim list --roles role1 role2 --scene test2        # 查一组入座
python3.11 -m rolesim run --roles role1 role2 --scene test2 --out runs/x
python3.11 -m rolesim run --roles role2 role1 --scene test1 --out runs/y   # 换座位
```

`--roles` 按座位顺序写两个编号或文件路径，`--scene` 写一个。新增角色或剧情只需要放一个新文件，不用改代码。入座检查（`fit_cast`）里，错误会阻止运行（例如座位数不对、同一角色坐两个座位、机制先验与启用的机制卡不一致、开场设定用了环境保留的 id）；提示只报告，例如"这个 skill 在该剧情里永远不会被激活"。运行记录 `manifest.json` 的 `origin` 字段记下用了哪些角色文件和剧情文件及其哈希。

给环境组接入用的是 `rolesim.roles.seat(roles, scene, backend)`：每个座位返回一个配置好的 Agent（剧情的可选动作、自己和对方的座位名、角色的 skill 和开场设定），以及首轮 `step` 要带的 `role_profile`。之后环境按合同 v0 调 `step` / `perceive`，接口不变。

### 没有环境标注时，线索从哪来

脚本时代，事件带着环境标注的线索（压力、不确定、冲突……），机制卡和 skill 按线索激活，紧张度按压力更新。自由对话里对方的话不带标注，所以角色在决策前先做一次**感知评价**：模型站在这个角色的立场，报告它从这句话里感到哪些线索、各多强（0–1）。程序只接受登记过的五种线索和合法范围，再按原有公式更新状态；状态变化仍引用这句话的事件 id 作证据。评价提示在三档消融里完全相同，因为它决定的是三档都要计算的状态。对方的话是"说法"，不是兑现证据，所以不会改变信任（信任只认可核验的兑现 / 失约记录）。

## 机制卡审定模板

```yaml
id: trust_revision
source: 决策机制库 3.4
status: proposed
psychological_hypothesis: 重复失约后更倾向先核查，兑现证据可支持有限恢复
stable_inputs:
  - 核查倾向
  - 关系的重要性
dynamic_inputs:
  - 对该对象的可靠性判断
  - 可见的承诺与兑现历史
trigger:
  observable_condition: 两次明确承诺均未在约定时间兑现
  insufficient_condition: 仅听到别人抱怨此人不可靠
options: [核查, 缩小授权, 协商修复, 暂停合作]
exceptions:
  - 角色观察到不可控外部障碍
  - 紧急共同目标要求暂时继续合作
updates:
  - 可靠性判断改变，不能据此直接覆盖善意或能力判断
observable_anchors:
  - 请求具体兑现证据
  - 提出可逆的小范围合作
counterexample:
  - 一次道歉就无依据地完全恢复信任
reviewer: 待填写
calibration: 待实验；不得把模板当已验证规律
```

该模板是供讨论的设计格式；v0.1 注册表位于 `rolesim/mechanisms.py`，并不直接读取上述 YAML。先确定规则，再决定是否迁移为数据驱动的执行配置。

## 当前字段到底用于哪里

| 字段 | 当前用途 | 未实现部分 |
|---|---|---|
| 30 分面（`traits.personality`） | 完整校验；4 分面编译条件化语句；合作分面参与卡片排序 | 其余分面的完整行为投影 |
| 依恋两轴（`traits.attachment`） | 存储与范围校验 | 依恋特异触发、关系工作模型 |
| 动机基线、施瓦兹价值、核心目标 | 控制器可见；价值与目标不进入角色自知和表达提示 | 需要满足度、目标效用、价值冲突求解、冲突阈值的使用 |
| 情绪敏感度/恢复（`traits.affective_capacities`） | 参与事件后紧张更新 | 多维情绪、调节策略成功率 |
| 核查偏好（`traits.cognitive_style`） | 条件化语句、verify 排序 | 自然语言证据强弱与误信修订 |
| 表达基线与情境规则（`speech_style`） | 条件化风格、boundary 排序；情境规则进入表达提示 | 更丰富语言风格与残差建模 |
| 71 维能力 | 模块状态 not_modeled | 定义、评分、能力门和压力影响 |
| 发展位置、荣格功能、道德推理、文化取向 | `module_status` 记录 not_modeled 及原因 | 全部待审定与实现 |

## 第一批共同审定材料

建议每位人物准备三个短场景：低压力基准、同内容高压力、出现纠正证据后的恢复。另做信息可见/不可见对照。每个场景允许多个可接受行动，并要求说明“什么条件下属于合理变化”。

首批需要补齐：原引用的 71 维定义文件；两到三个真正希望研究的角色材料；五张机制卡的强/弱触发和例外；哪些字段能给角色知道、哪些仅供系统施加行为约束。服务器地址与模型选择是后续配置，不影响本地结构审定。
