# 待定：角色的持续对话（会话记忆）与运行提速

2026-10-20 起草，2026-11-10 按现在的分阶段管线更新。**只记录，暂不实施。** 起因：担心"每次调用都是新的"会很慢、轮数多了难控长度，希望角色和模型的交互像聊天一样能接着说。现在的调用链见 [docs/06-runtime-flow.md](../docs/06-runtime-flow.md)。

## 0. 背景：聊天式交互本身是怎么做的

聊天助手里的模型本身也不保留会话。每次回复，客户端把系统说明、全部历史和新消息一起重新发送；模型生成完就结束。看起来连续，靠的是三件事：

1. **客户端保存消息列表**，每轮只在末尾追加；
2. **前缀缓存**：推理服务复用与上次一字不差的前缀的计算结果（KV cache），只计算新增部分；
3. **超长时压缩**：把较早的内容整理成摘要，原始记录另存，需要时再查。

## 1. 现状

- 每次行动的调用：每个记录组一次 S1，有反馈时一次 S3，一次 S2，一次表达，每个阶段有数值槽位时再加一次选值。两人 8 次发言用 Qwen3-8B 实测为 48 次调用（S1 15、values 11、S2 8、表达 8、S3 6）。
- 单次调用 30—90 秒（思考模式），主要花在生成思考内容上；2026-10 的旧管线实测输入只有几千 token，预填充不到 1 秒，前缀缓存命中率约 39%。
- 每次调用都是独立请求：一条 system + 一条 JSON 载荷，不累积多轮消息。
- 长度已有上限：表达只看最近 12 条记录；证据门至多取回 4 条记忆；提示里的 schema 是精简版（约 2—3k 字符）。

结论没有变：**瓶颈是生成思考内容，不是重发上下文。** 只改成聊天式，省下的是不到 1 秒的预填充。

## 2. 可选做法

### S1 每个角色一条持续对话（会话记忆）

- 每个角色保存自己的消息列表，只追加；画像放在 system 前缀里保持不变，以命中前缀缓存。
- **每个角色至少两条线，不能合成一条**：内心线（S1 / S2 / S3 / 选值，看得到想隐瞒的内容）与说话线（表达，只见可以说出的部分）。合成一条会让隐瞒原文进入表达上下文，违反隔离规则和 `concealed_withheld` 审计的前提。
- 超过长度预算时把较早轮次压缩成摘要；摘要须落盘，并保留所依据的记录编号，否则状态更新的证据链断开。
- 历史里不放回模型的思考内容（与现在"推理只进轨迹"一致）。
- 收益：更接近真实对话；速度收益小。代价：提示随轮数增长、需要压缩规则，轨迹和审计要能读这种格式。

### S2 减少每次行动的调用数

- 选值调用并入下一次调用：不行，选值必须在算子生成槽位之后、写入之前，并入会让模型提前看到区间之外的东西或让选值依赖未提交的状态。
- 同一次行动里多个记录组的 S1 合成一次：调用数随记录组数下降最明显（三人场景尤其）。代价是一次 S1 要对多组记录分别给出产物和判断，C4（同一事件阶段读同一份快照）的含义要重新说明。

### S3 限制思考长度

给思考部分设 token 上限。需要先做有 / 无上限的效果对比；关闭思考后效果明显变差，上限不能低到等于关闭。

### S4 多场运行并行

一场对话里角色只能依次行动，无法并行；但 vLLM 能同时服务多条请求，同时跑多场运行（不同剧情、模式、有 / 无 skill），总耗时接近单场。批量消融实验收益最大。需要：运行入口支持批量与并发上限，运行目录同一秒启动时另加区分（即 [01](01-engineering-backlog.md) O4 的实验调度器）。

## 3. 必须守住的约束

- 隐瞒信息只进 S1 / S2 / S3，不进表达；别人的设定、状态、思考永不进入本角色的任何调用。
- 每条状态变化仍须引用本角色可见的记录编号；压缩摘要不能成为新的证据来源，只能指回原始记录。
- 所有模型输入输出完整落盘，运行可复核。
- 不静默改变消融模式的含义；改动后同步 docs/ 与评测说明。

## 4. 待作者确认

1. 是否做 S1；若做，长度预算和压缩触发点怎么定。
2. S2—S4 的先后。若目标是批量实验更快，建议 S4 优先。
