# 待定：角色的持续对话（会话记忆）与运行提速

2026-10-20。**只记录，暂不实施。** 起因：作者担心"每次调用都是新的"会很慢、轮数多了难控长度，希望角色和模型的交互像聊天一样能接着说。本文记下现状实测、可选做法和必须守住的约束，开工前再确认。现状调用链见 [docs/06-runtime-flow.md](../docs/06-runtime-flow.md)。

## 0. 背景：聊天式交互本身是怎么做的

聊天助手里的模型本身也不保留会话。每次回复，客户端把系统说明、全部历史和新消息一起重新发送；模型生成完就结束，"等待"期间模型什么都不做。看起来连续，靠的是三件事：

1. **客户端保存消息列表**，每轮只在末尾追加；
2. **前缀缓存**：推理服务复用与上次一字不差的前缀的计算结果（KV cache），只计算新增部分；
3. **超长时压缩**：把较早的内容整理成摘要，原始记录另存，需要时再查。

## 1. 现状实测（运行 `20261020-204914_test1_Qwen3-8B`）

| 每次调用 | 输入长度（字符） | 思考内容（字符） |
|---|---|---|
| 感知评价 appraise | 约 2000–3400 | 1000–2700 |
| 决策 decide | 约 5500–6800 | 500–1800 |
| 表达 express | 约 1300–2800 | 700–1100 |

- 每次调用都是独立请求：`ChatBackend._call` 只发一条 system + 一条 JSON payload，不累积多轮消息。
- 输入只有一两千到四千多 token，vLLM 预填充不到 1 秒；日志显示前缀缓存命中率约 39%。
- 单条请求生成速度约 45 token/s。每次调用要先生成数百到一千多 token 的思考，单次 20–60 秒；每次发言 3 次调用，约 2 分钟。
- 长度已有上限：`visible_history` = 前情 + 最近 12 条（`memory.WINDOW`）+ 召回 4 条（`memory.RECALL_K`）。超过 12 条后输入不再增长。

结论：**瓶颈是生成思考内容，不是重发上下文。** 只改成聊天式，省下的是不到 1 秒的预填充。

## 2. 可选做法

### S1 每个角色一条持续对话（会话记忆）

- 每个 Agent 保存自己的消息列表，只追加；人物画像放在 system 前缀里保持不变，每轮追加"对方刚说的话 + 当前状态"，以命中前缀缓存。
- **每个角色两条线，不能合成一条**：内心线（评价 + 决策，可见 `keep_private`）与说话线（表达，只见可透露信息）。合成一条会让隐瞒原文进入表达上下文，违反现有隔离规则和 `concealed_info_withheld` 审计的前提。
- 超过长度预算时把较早轮次压缩成摘要；摘要须落盘，并保留所依据的事件 id，否则状态更新的证据链断开。
- 历史里不放回模型的思考内容（Qwen3 官方对多轮对话也是这样建议的；与现有"推理只进运行记录"一致）。
- 收益：更接近真实对话、上下文连贯；速度收益小。代价：提示随轮数增长、需要压缩规则、`audit.jsonl` 要记录完整消息列表，审计和评审包要能读这种格式。

### S2 感知评价与决策合成一次调用

每次发言从 3 次调用变 2 次，耗时约减三分之一。代价：评价与决策的输入输出要在一次返回里分开校验，审计里两者的记录格式要调整；消融档位下"评价提示三档相同"的约定需要重新表述。

### S3 限制思考长度

给思考部分设 token 上限（服务端或请求参数）。需要先做有 / 无上限的效果对比；作者已说明关闭思考后效果差，上限不能低到等于关闭。

### S4 多场运行并行

一场对话里两个角色只能依次发言，无法并行；但 vLLM 能同时服务多条请求，同时跑多场运行（不同 seed、档位、有 / 无 skill），总耗时接近单场。批量消融实验收益最大。需要：运行入口支持批量与并发上限、各运行目录互不干扰（时间戳命名已支持，同一秒启动需另加区分）。

## 3. 必须守住的约束

- 隐瞒信息只进评价和决策，不进表达；对方的设定、状态、思考永不进入本角色的任何调用。
- 每条状态变化仍须引用本角色可见的事件 id；压缩摘要不能成为新的证据来源，只能指回原始事件。
- 所有模型输入输出完整落盘，运行可复核。
- 不静默改变消融档位的含义；改动后同步 [docs/07-architecture.md](../docs/07-architecture.md) 与评测说明。

## 4. 待作者确认

1. 是否做 S1；若做，长度预算和压缩触发点怎么定。
2. S2–S4 的先后。若目标是批量实验更快，建议 S4 优先，其次 S2。
